## Deviations

1. **Plan said:** `summon snapshot save --dir … --layout … --launch <id>` is invoked by the trap and handled by `src/commands/runtime.ts`. **Found:** the global flag parser (`src/cli/parse.ts`) rejected `--dir` ("Unknown flag"), and `--layout` was consumed as the global layout flag and validated as a preset, so the trap's snapshot save has been failing silently (stderr goes to `/dev/null`) on develop and in the released v1.9.0 (verified against `main` at `5cca1ea`: `node dist/index.js snapshot save --dir /tmp --project x --layout y` exits 1). **Chose:** `--dir`, `--project` and `--launch` are registered global string options, and `parseCli` skips the `--layout` preset validation for the one subcommand where the flag is a label (`snapshot`; older traps still pass the recorded layout label there), so `snapshot save` reads its flags from `values` like every other subcommand and keeps `--help`, `--version` and unknown-flag diagnostics. Overrides are built for every subcommand before dispatch, so the validation cannot live in `buildOverrides`. **Why:** the generation-checked write is the Phase 1 contract and the real-process interleaving test could not pass without it. Covered by `src/cli/parse.test.ts`, `src/commands/runtime.test.ts` and an `index.test.ts` integration case.
2. **Plan said:** `bootstrapLine(project, launchId, backend)`. **Found:** the Rex root pane-file write needs the root pane name. **Chose:** `bootstrapLine(project, launchId, backend, rootPaneName?)`; it throws when `backend === "rex"` and the name is missing. Routine signature correction.
3. **Plan said:** `script.test.ts` expectations change only in the bootstrap and trap `it` blocks, and `src/script.ts` changes only inside `emitRootPanePidBootstrap` and `emitCleanupTrap`. **Found:** the emitters need the launch id, so `generateAppleScript`/`generateTreeAppleScript` take a trailing `launchId` parameter and throw when a `projectName` is given without one (a launch id is never optional for a tracked workspace). **Chose:** the `script.ts` diff is: the two emitter bodies, one import, the `requireLaunchId` helper, the seventh parameter on both generators and their four emitter call sites; the generated text differs only in the two typed lines (proved by `src/dry-run-parity.test.ts`). Every `script.test.ts` call that passes a project name now also passes a fixed `LAUNCH_ID`; assertions outside the trap blocks are unchanged. `launcher.test.ts` `toHaveBeenCalledWith` assertions on the generators gained the seventh argument (`expect.stringMatching(LAUNCH_ID_RE)`).
   **Dry run and detection (behavior change, recorded):** backend detection now runs for `--dry-run` too (P15 puts it first; P2 makes dry-run print what a real run would do). Two consequences: (a) inside a Rex terminal with the Rex CLI present, `--dry-run` fails with "Rex backend is not available in this version" like a real launch, until Phase 2 adds the Rex dry run; (b) on a machine with neither Ghostty.app nor the Rex CLI, a real launch fails naming both, but `--dry-run` falls back to the Ghostty script with a notice ("... Dry run continues with the Ghostty script."), so dry runs keep working on CI runners and in other terminals as before. `index.test.ts`, `launcher.test.ts`, the parity test and the interleaving test pin `TERM_PROGRAM=ghostty` so the suites exercise the Ghostty path regardless of the terminal that runs them.
4. **Plan said:** `GhosttyBackend` is a pure move of dispatch. **Chose:** `src/backends/ghostty.ts` holds the post-dry-run Ghostty half of both layout launches (guards, command resolution, script generation, execution) plus `executeScript`, the launch spinner helpers and `closeWorkspaceWindow`, which moved with it. `launcher.ts` re-exports the three public helpers so existing imports and tests keep working. The dry-run branch and the pane-name computation stay in `launcher.ts`.
5. **Plan said:** the write protocol's `{ launchId: null }` means no record file exists. **Chose:** a malformed record file also counts as present (the check is `existsSync`, not "parses"), so a corrupt file is never silently replaced by an adopter. A test pins this.
6. **Plan said:** a Rex record's liveness comes from `sessionState` (Phase 3). **Chose:** until then `readStatus` resolves `backend: "rex"` records to `unknown` with the reason "Rex liveness is not available in this version"; no consumer treats `unknown` as live.
7. **Plan said:** the `readAllStatuses` discovery row is an "unverified launch". **Chose:** the row carries the manifest's project, directory, layout, panes, `launchId`, `backend`, `state: "unknown"`, `uptime: null`, `pid: 0` and `reason: "unverified launch"`. Manifests of a project that has a record are not listed (orphan adoption is Phase 3).
8. **Plan said:** the interleaving tests forward `--launch` to a Node helper running the `runtime.ts` path. **Chose:** the shim forwards to a private tsup bundle of `src/index.ts` built into the test's temp directory (`src/fixtures/build-cli.ts`), so the real CLI parse and handler run and two suites never race the shared `dist/` build. The dry-run parity test uses the same helper and a pinned develop fixture (`src/fixtures/dry-run-develop-f5f7901.txt`). Both fixture-repo suites build their git environment from `gitSafeEnv()` (no `GIT_DIR`/`GIT_INDEX_FILE`): under the pre-commit hook git exports those, and a plain `process.env` spread made the fixture commits land on the feature branch during the first commit attempt (recovered with `git reset --soft`).
9. **Plan said:** `discardStatusRecord` takes `{ launchId }` from a caller that has one. **Chose:** the launcher's failed-publish path calls it with `"replace"` on purpose: after a failed `writeStatus` the file still holds the previous generation, so `{ launchId: <new> }` could never match and the stale record would survive. The function accepts a `launchId` for callers that must abstain on mismatch (Phase 5).
10. **Security gate:** `src/shell-escape.lint.test.ts` gained a region rule: inside a `// --- Shell fragments` section every interpolating line must route through a quoting helper (`shellDoubleQuote`, or the region's own `shellLaunchId`/`shellArtifact`/`shellLaunchDir`/`shellPaneFile`/`shellLogFile`/`paneFileLine`) or carry a `lint-allow-escape` marker, and the gate asserts that `src/launch-identity.ts` still carries the region header. Four markers remain, all in `src/launch-identity.ts`: the quoted pair returned by `shellPaneFile` (path built on the checked line above), the `paneFileLine` command (both paths from `shellPaneFile`), the `onStop` line (trusted command fragment, the same decision develop documented) and the final `__summon_cleanup` composition (individually checked parts). `paneFileLine` additionally validates the pane name against `PANE_NAME_RE` (exported from `src/tree.ts`) so the shell-side path is confined on its own.
11. **Simplify pass (reuse, simplification, efficiency, altitude; four fresh-context reviewers):** applied: `confinedPath` in `src/utils.ts` replaces three copies of the path-confinement check; `isPlainText` in `src/pane-inventory.ts` is shared by the native and Rex identity parsers; detection probes are thunks the table calls only on the rows that need them (no `which rex` on a `TERM_PROGRAM=ghostty` launch); `resolveBackendForLaunch` returns the `Detection` union instead of throwing, so the dry-run fallback branches on `ok` and keeps the table's notices; `LaunchContext` is the successful `Detection` rows; the two layout launchers take one `LaunchInputs` object; the Ghostty backend returns `NativeMetadata | undefined`; `readAllStatuses` lists `STATUS_DIR` once; `ResolvedStatus.pid` is `number | null` (null for an unverified launch; the on-disk record keeps `pid: number`); `snapshot save --launch` collects the git state before taking the status lock and writes inside it; `vitest.config.ts` pins `TERM_PROGRAM=ghostty` for every suite instead of per-spawn env edits; `launcher.test.ts` mocks `resolveBackendForLaunch` instead of steering the table through `which`/`existsSync`. Skipped on purpose: a single global CLI build shared by the subprocess suites (`globalSetup`) and dropping `afterErrors`, `statusTestHooks.beforeLock`, `endedAt`, the manifest reader/writer and `resolveBackendForRecord` (all named Phase 1 deliverables or protocol parts), and lazily skipping the record read on `"replace"` (the plan's protocol reads the current record in every transaction).
12. **Phase 4 note:** a Rex record resolves to `unknown` (deviation 6), but `classifyState` in `src/monitor.ts` still maps every non-active state to "stopped"; Phase 4 wires `unknown` and `partial` through every consumer (plan P10).
13. **Phase 2 note:** `src/backends/rex/types.ts` (the `RexIdentity` type and its parser) was created in Phase 1 because the status record validation needs it; Phase 2 adds `RexOp`, `RexResult` and `RexFailure` to the same file.
