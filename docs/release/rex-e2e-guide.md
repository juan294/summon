# Rex end-to-end guide (v2.0.0 candidate)

Candidate: local `develop` at the commit named in §2.3 (Rex backend, six phases, four validation rounds, the guide findings fixed). This guide is the test contract for the Rex release: an automated part that Claude runs and records here, then a manual part that the owner runs only after every automated item is green. It complements `docs/rex.md` (the user-facing Rex contract) and `docs/release/release-checklist.md` (the release procedure, which stays authoritative from the release PR onward).

Sequencing rule: no manual step starts while an automated item is red or pending. A manual finding goes through the ordinary implement, review and verify loop, after which the automated part is rerun in full before manual testing resumes.

## 1. Harness and safety contract

- **Always run the candidate, never the global 1.9.0.** Inside the repo use `./dist/index.js <args>` after `pnpm build` (or `npm link`, M0). For a throwaway state run it with another home: `HOME=$TMPDIR/summon-rc-home ./dist/index.js <args>`; the untracked helper `scripts/summon-rc.sh` (present only in the primary checkout, excluded through `.git/info/exclude`) wraps exactly that. A sandboxed home keeps the owner's real `~/.config/summon` (projects, trust, status, cache) untouched, with the Rex limits of the next two bullets.
- **Run Rex tests from a Rex terminal.** With Ghostty installed, Summon picks Ghostty in every terminal except a Rex one (detection table in `docs/rex.md`). Open a block in Rex Beta and run the candidate there. The Rex terminal exports `REX_SERVER`, which Summon honors inside Rex, so even a sandboxed `HOME` still reaches the real server. Scripts and the automated suite set `TERM_PROGRAM=rex` and `REX_SERVER` explicitly for the same reason.
- **Disposable projects only, in an isolated home.** Every test project is a directory under `$TMPDIR` named `rc-<topic>` (manual, registered in the isolated home `$RC` of M0), `summon-e2e-<id>` (the native and lifecycle suites) or `e2e-<id>-<name>` (the CLI suite; the status table shows 16 characters of a name). The suites and the owner destroy only sessions labelled with those names. Never kill, select or close the owner's own sessions (today: `amber-creek`; the name changes with every Rex window).
- **The pane shells resolve `$HOME` themselves.** The bootstrap and the cleanup trap are typed shell text with `$HOME/.config/summon/...` paths, and a Rex block inherits the server's environment, not Summon's. A Summon run under a sandbox `HOME` therefore never sees its pane files unless the sandbox is handed to the blocks: the CLI suite and the manual part both set the `env.HOME` config key to their sandbox (§4 F3; M0 does it for `$RC`). The real `~/.config/summon` is never read or written by a test; only M11's last item uses it, by the owner's choice.
- **Never quit or restart the Rex app or server as part of an automated step.** The manual part has two steps that do (M3.5, M5.6); the owner runs them from a surviving Terminal.app window with the Rex environment set by hand, and reopens the app afterwards.
- **One Rex suite at a time.** `rex-native`, `rex-lifecycle` and `rex-cli` share the server; run them as separate commands, never in one `vitest run`. An interrupted `rex-cli` run leaves its `e2e-<id>-*` sessions and its `summon-rex-cli-*` temp directory behind (the cleanup runs only at the end): kill and remove them by hand.
- **Cleanup is proven, not assumed.** Each suite records the sessions it creates, kills them at the end together with any session labelled with its prefix, and polls the server until they are gone (C20). A kill the server rejected, a session still listed or a listing that did not answer fails the suite; `rex-cli` then keeps its sandbox with a `RECOVERY.json` naming the server, the prefix and the sessions to kill. A lookup that did not answer is never read as "absent" inside a scenario either. The manual part ends with the same proof (M12).
- **A quiet machine.** The Rex server answers a `session.view` in about 50 ms, but under heavy concurrent load (load average above 10 on this Mac while other agents ran, 2026-10-30) its first view of a session whose shells are still starting stalled past Summon's 8 s read window once in several runs. Summon reports that honestly (`unknown`, `could not be verified`, `session.attach request timed out`) and changes nothing, so such a failure is an environment condition: note the load average the harness prints at the top of the log, and rerun when the load is below the core count. The 8 s window itself was raised from 3 s on this evidence.
- **Evidence.** Each automated run writes its log under `logs/rex-e2e-2026-10-30/` in the primary checkout (gitignored, kept on this machine) and its result line to §2.3 of this guide (exit codes, counts, coverage, the Rex build). The harness prints `tree <sha>[+dirty]` and the load average on the first line of every Rex log. The run wrapper appends `exit=<code>` and a `leftovers:` line after each suite: `status` is `ls ~/.config/summon/status | grep -c e2e` (test projects in the real home), `sessions` is `rex ls | grep -c 'e2e-'` (the suites label sessions `e2e-<id>-*` or `summon-e2e-*`; the owner's sessions never match), `sandboxes` is `ls -d $TMPDIR/summon-rex-cli-* | wc -l`; all three must be 0. Run A7 without M0's `npm link` active: C10a's control checks that the `summon` the pane resolves is not the candidate, and a linked candidate on PATH would weaken it. Manual results go in §3 with the date and the observed output when it differs from the expectation.

## 3. Manual part (run by the owner, after §2 is green)

Tags: **Rex** = run from a block inside Rex Beta; **Ghostty** = run from a Ghostty tab; **Other** = run from Terminal.app or iTerm; **Visual** = needs eyes on the app; **TTY** = needs an interactive terminal. Every `rc` below is the candidate under the isolated home of M0, never the released 1.9.0 and never your real `~/.config/summon`. Replace `[ ]` with `[x]` or a short note.

Two terms used by the rows. **Reset** = `rex ls`, `rex kill <id>` for every `rc-*` session listed, then `rc status --once` (every `rc-*` row `stopped`). **Fresh launch** = a reset, then the `rc` launch command of the row: a plain `rc <project>` while that project's session still exists switches to it instead of launching (M3.1), and it does so for a partial session too (one whose root block is closed), so a row that needs a new session must reset first or use `--new-window`. Config resets use `rc set <key>` without a value: `rc set <key> ""` is rejected with exit 1 for the command keys, `on-start`, `on-stop` and `starship-preset`.
