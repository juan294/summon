## Risk hypothesis

Cutting a label can damage it (surrogate pairs, combining marks, exact limits), make the dry run differ from the real request, or cut the command. Making the same-checkout check more permissive can accept a really different checkout, or let a path in another case write a record under another name. Notes that predict a real run can be false for some record state or entry point. Moving the live-ports wording from "server" to "pane" can leave a path that still blames the server, or a check mark over an incomplete read.

## Findings

**F1 (S3). A pane command with a control character (a tab) launches, but Summon cannot read its own record afterwards.** `summon set editor $'sleep 300\tx'`, then `summon <dir> --layout minimal`: exit 0, "ready in Rex". A second launch exits 2 with "alpha is recorded in Rex but the record has no Rex identity; run summon alpha --new-window to relaunch", `focus` and `inspect` exit 2, `status` shows `unknown`, and "invalid Rex identity discarded" is printed one to three times per command. Expected: the workspace it just opened can be switched to and focused. Cause (read in source): the label keeps the tab, and `src/backends/rex/types.ts` rejects a record when `isPlainText(block.label)` fails; `blockLabel` cuts but does not clean. 2.2.1: the same for titles up to 128 characters; a longer title was refused by the server before, so for long commands this state is new in 2.2.2. A control character after position 127 is cut off and is harmless. Whether a real Rex server accepts a tab in a label is not verified (the fake accepts it). Workaround: remove the tab, then `--new-window`. Not listed as a known issue.

**F2 (S3). A path typed in another letter case takes another project name, with more than naming effects.** Cases, all run: (a) `mine` registered to one/alpha and live, then `summon .../ONE/alpha` creates a second session [alpha] for the same checkout (2.2.1 the same). (b) `alpha-two` registered to two/alpha and live, [alpha] live from one/alpha, then `summon .../TWO/alpha` exits 2 with "Register .../TWO/alpha under a different name", although that checkout is registered and running as alpha-two. (c) `alpha` registered and claiming port 3000 in package.json, its record ended, then launched as one/ALPHA and listening on 3000: `summon ports` prints "Port 3000 is held by ALPHA/editor (node); alpha (package.json) claims it", and `summon doctor` prints FAIL for the project's own port (2.2.1 the same). (d) With [alpha] live, `summon .../one/ALPHA --new-window` now succeeds and rewrites `alpha.json` as project ALPHA, so `status` shows ALPHA active and alpha stopped; 2.2.1 refused this step. Expected: one checkout keeps its registered name. Cause (read in source): `resolveProjectName` in `src/launcher.ts` compares `resolve()` strings and does not use `sameProjectDirectory`. Workaround: the on-disk case or the project name. Partly listed as a known issue (S4: the name as typed, and both names in `status`); the second session, the refusal of a registered checkout and the false conflict in `ports` and `doctor` are not listed. No different checkout was accepted in any case.

**F3 (S4). `summon open <name> --new-window --dry-run` previews a new session without a note, and a real run does not create one.** With [alpha] live and registered, the dry run prints the `session.create` request and no note; the real `summon open alpha --new-window` prints "Switched to [alpha]". With an unverified record, or one without a session id, the real run exits 2; the dry run again prints no note. The note "a real run refuses to launch over it (--new-window replaces it)" is likewise untrue for `summon open`, which refuses with `--new-window` too; `summon <dir> --new-window` does replace it. Cause (read in source): `recordedNote` in `src/backends/rex/backend.ts` follows the launch decision, while `open` focuses a running workspace first and ignores the flag. 2.2.1 printed the switch note here, which was true for a live record, so the missing note is new; the real behavior is unchanged. No state is changed. Not listed. Workaround: preview with `summon <dir> --new-window --dry-run`, or omit the flag with `open`.

**F4 (S4). `summon inspect` still blames the Rex server when one pane answers that it has no `ports` method.** With the editor answering with port 3000 and the sidebar answering `has no method "ports"`, `inspect` prints `ports: 3000 127.0.0.1 (node)` followed by `live ports: this Rex server has no live ports (needs API 16 or later)`. With the order reversed it stops and never reads the second pane, while `summon ports` on the same state reads 3000 and prints "1 terminal pane does not support live ports". When every pane answers that way although `api describe` knows the method, `ports` also keeps the server message with status `unsupported`. The changed behavior holds for the reply status `unsupported`, which is the form 2.2.2 fixes. 2.2.1 the same. Whether a real server mixes these answers is not verified. Not listed, and the CHANGELOG sentence "still reads the others" holds only for the status form. Workaround: `summon ports`.

Verified statements of the release notes and CHANGELOG (run against 2.2.1 and 2.2.2):

- Labels: titles of 127 and 128 code points are kept, 129 and more are cut to 127 plus the ellipsis (ASCII, wide, emoji, combining, ZWJ, variation selector, bidi). No surrogate pair is split, `[...label]` is never above 128, the whole command is in the request, and dry-run label, real label, record label and manifest label are equal. Tree layout panes and an autodetected minimized pane too. 2.2.1 failed at 129 with the server's refusal.
- Paths: 15 spellings of one checkout switch (parents and the checkout in another case, relative, trailing slashes, `..`, symlinks, `/tmp`, the `/System/Volumes/Data` path); two/alpha, TWO/alpha, two/ALPHA, `../two/alpha` and three/alpha are refused in both versions, with `--new-window` as well. `open`, `switch` and the picker accept a registry entry in another case. 2.2.1 refused the ten spellings that type another case (or the `/System/Volumes/Data` path) and accepted the symlink, `.` and `..` ones.
- Notes: true for `summon <dir>` in every tested state; `new-window=true` from config keeps the note, and the real run switches. The picker shows the order hint, and the note for a recorded, unregistered row matches live, partial, stopped, unverified and no-session-id outcomes.
- Ports: status and wording are as stated for mixed and all-unsupported panes; the check mark is gone for every incomplete read and for unverified workspaces, which are named in `ports` and as INFO in `doctor`; stopped and ended workspaces keep the check mark.
- Session symlink: `list` and `show` follow it, `add` refuses to replace it. In Bash, closing the pty ran the on-stop hook twice, as the known issue says.
