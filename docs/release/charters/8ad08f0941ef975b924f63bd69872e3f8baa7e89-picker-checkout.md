## Risk hypothesis

The v2.2.0 picker work adds a palette action that shells out to `summon list --json`, makes `--dry-run` previews of `open`, `switch` and the picker bypass focus and reconciliation, and adds a guard that refuses to switch to or replace a live or unverified workspace recorded for another directory under the same name. Failure modes explored: the printed Lua differs from the shipped file; `list --json` is malformed for unusual paths; a preview focuses, reconciles or writes status; the guard is bypassed through trailing slashes, relative or `..` paths, symlinks or case variants, or through one of the entry points (launch, `--new-window`, `open`, `switch`, picker, status Enter); concurrent launches from two checkouts produce two sessions or two records; copy claims an outcome the command does not deliver; residue is left behind.

## Findings

**F1 (S3). A case-variant path to the same checkout is refused as a different checkout.** On the default case-insensitive APFS volume, `.../projects/ONE/alpha` and `.../projects/one/alpha` are the same directory (same inode, 162011687). With [alpha] live from one/alpha, `cd .../projects/one && summon .../projects/ONE/alpha --layout minimal --editor true --sidebar true` exits 2 with "Workspace [alpha] belongs to .../projects/one/alpha. Register .../projects/ONE/alpha under a different name with 'summon add <name> <path>'." The same happens for `summon open alpha` after `summon add alpha .../projects/TWO/alpha` while the record is `.../projects/two/alpha`. The guard fails closed (nothing is replaced or focused), but the message tells the user it is a different checkout. `sameProjectDirectory` in `src/project-directory.ts` compares `resolve()` strings and then `fs.realpathSync`, which keeps the typed case; `fs.realpathSync.native` returned the on-disk case (`.../one/alpha`) in a probe. Workaround: launch or register with the on-disk case.

**F2 (S4). The dry-run note promises a switch that a real run refuses.** With [alpha] live from one/alpha and alpha registered to two/alpha, `summon open alpha --dry-run` (and `summon . --dry-run` in two/alpha) prints "-- Note: alpha is recorded as a Rex workspace (session:...); while it is running, a real run switches to it instead of creating this one". The real `summon open alpha` and `summon .` exit 2 with the different-checkout refusal. The same note appears when the record cannot be verified, where a real run also refuses. No state is changed; the wording is wrong for these two states.

**F3 (S3). The dry-run picker previews an unregistered recorded workspace under a different name.** With [alpha-one] live from one/alpha and then `summon remove alpha-one`, `summon open --dry-run` lists "4  alpha-one → .../one/alpha". Choosing 4 previews a launch labelled `"label": "alpha"`, `"window_label": "[alpha]"` (the directory basename) and adds the F2 note about alpha's session from the other checkout. The real `summon open` picker shows the same row as "2 ● alpha-one active" and choosing it prints "Switched to [alpha-one]". The preview therefore shows a different project name and a different outcome than the real choice. This row type is new in v2.2.0 (CHANGELOG: the dry-run picker "also lists recorded workspaces that are not registered"). No state is changed.

**F4 (S4). The dry-run picker and the real picker number the same projects differently.** `summon open --dry-run` lists registry order (1 beta, 2 alpha, 3 weird), while `summon open` sorts live rows first (1 alpha, 2 beta, 3 weird). A user who previews "1" and then types "1" in the real picker gets another project (here, a focus of alpha instead of a launch of beta). Each list shows its names, so the user can read the right number.

Observations that are not findings:

- Ended launches left manifests reported as "never confirmed its session" (`summon status --once`, `summon clean alpha --orphans`). This comes from the fake: its panes never run, so no pane file is written and the cleanup trap never fires when the test removes a session from the fake state. The same happened for the same checkout, so it is not tied to the guard.
- One expect run of `summon status` stopped responding to SIGTERM and SIGINT. The expect script had stopped reading the pty after its timeout, so the TUI's synchronous TTY write blocked the event loop. A corrected run (Enter, dismiss key, `q`) exited 0 and showed "Focus failed:" plus the different-checkout sentence. Harness artifact.
- An unverified record (rex answering "connection refused") refuses `open` and a launch from the other checkout with the "could not be verified" message, without naming the checkout conflict. It refuses either way.
- A stopped record from another checkout is replaced by a launch, as documented ("a live or unverified workspace").
